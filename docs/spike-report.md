## 1. 結論摘要

| 問題（SDD 第 12 節） | 結論 |
|---|---|
| 免費版能不能用原生 `computer_use`？ | **能，但不穩定**：同一份截圖時而成功、時而回 400「安全違規」，無法預測 |
| 自訂函式（`custom_fc`）點擊準不準？ | **很準**：3.5 Flash-Lite 命中 8/8，平均誤差 1.1 px；3.6 Flash 有回應的 4 次全部命中 |
| 免費版的實際配額？ | **非常少**：Hydrogen 與 3.6 Flash 都只有每天 20 次；3.6 Flash 每分鐘 5 次 |
| Decisions API 判斷畫面準不準？ | **非常準而且快**：畫面狀態 14/14、高風險按鈕 6/6，每次約 0.6 秒 |
| 只用 Decisions API 能不能決定點哪裡？（spike 04） | **可以**：編號標記法在文字按鈕 8/8、純圖示 4/4，約 1 秒；但需要程式先找出候選，而且多步規劃仍要靠模型 |

**建議**：
1. 預設動作後端改用 `custom_fc`，原生 `computer_use` 只當備選。
2. 代理人模型的配額是整個系統的最大瓶頸，設計上要讓 Decisions API 和技能重播承擔大部分工作。
3. 調整模型分工（見第 4 節，需要你決定）。

## 2. 測試結果

### 2.1 模型能力（spike 01，含重跑與診斷）

| 模型 | 純文字 | 截圖＋自訂函式 | 回傳函式結果 | 原生 CU desktop | 原生 CU browser |
|---|---|---|---|---|---|
| `gemini-4-hydrogen` | ✅（35 秒） | ✅ 一次成功（45 秒）、一次逾時 | 未測到（配額用完） | ❌ 429 每日上限 | ✅（13 秒） |
| `gemini-3.8-flash` | ❌ 503 | ❌ 503／逾時 | 未測到 | ❌ 503 | ❌ 503 |
| `gemini-3.6-flash` | ✅（3–20 秒） | ✅（5–24 秒） | ✅（含圖片） | ❌ 400 安全違規 ×2 | ✅ 一次、❌ 400 一次 |
| `gemini-3.5-flash-lite` | ✅（5 秒） | ✅（3 秒） | ❌ 503 ×4 | ✅（5 秒） | ❌ 400 安全違規 |

- **3.8 Flash 整段測試期間都在 503 過載**，無法評估。要改天再測。
- **原生 `computer_use` 的 400「安全違規」是隨機的**：同一張合成畫面，3.6 Flash 的 browser 環境第一次成功、第二次被擋；3.5 Flash-Lite 則是 desktop 成功、browser 被擋。畫面裡沒有任何不當內容，推測是安全分類器誤判。
- **回傳函式結果的格式已確認可用**（`diag_function_result.py`）：純字串、文字列表、文字＋圖片列表都成功，`previous_interaction_id` 串接正常，模型收到結果後會正確呼叫 `task_done`。spike 01 裡的 503 是間歇性的伺服器問題。
- **原生 `computer_use` 回傳的動作名稱是 `click`、參數是 `x`、`y`**，座標系與自訂函式相同（0–999）。

### 2.2 點擊準度（spike 02，自訂函式）

8 張合成畫面，每張 7 個中文按鈕，請模型點指定的那一個。

| 模型 | 有回應的次數 | 命中 | 平均誤差（距按鈕中心） | 平均延遲 |
|---|---|---|---|---|
| `gemini-3.5-flash-lite` | 8/8 | **8/8** | **1.1 px** | **3.5 秒** |
| `gemini-3.6-flash` | 4/8（另外 4 次被 429 擋下） | 4/4 | 1.2 px | 18 秒 |

兩個模型點的位置幾乎都在按鈕正中心。

### 2.3 Decisions API（spike 03）

| 測試 | 正確率 | 平均信心值 | 平均延遲 |
|---|---|---|---|
| 畫面狀態分類（6 種狀態 + `unknown`，14 張） | **14/14** | 0.97 | 0.70 秒 |
| 紅圈按鈕是否高風險（6 張） | **6/6** | 0.90 | 0.74 秒 |

- 已知狀態的信心值都在 0.98 以上；不屬於任何狀態的畫面正確判斷為 `unknown`，信心值 0.83–0.87。
- 高風險按鈕（購買、刪除、送出）的 `noul` 為 0.85–0.93；一般按鈕（關閉、返回、下一頁）為 0.08–0.12，兩者區隔明顯。
- 結論：SDD 設計的「信心門檻 0.8」可行，但 `unknown` 本身的信心值也會超過 0.8，所以程式要判斷「選項不是 `unknown`」，不能只看信心值（SRS FR-602 已經有這個條件）。

### 2.4 只用 Decisions API 決定點哪裡（spike 04）

目的：不呼叫代理人模型，改由程式準備「候選清單」，讓 Decisions API 選出下一步要點的位置。測試畫面：8 張文字按鈕畫面＋ 4 張純圖示畫面（沒有任何文字，見 `icon_fixtures.py`）。

| 做法 | 候選怎麼來 | 畫面 | 正確 | 答對時的平均信心 | 平均延遲 |
|---|---|---|---|---|---|
| 文字候選＋直接指名（基準） | 每個按鈕的文字與大概位置（模擬 OCR） | 文字按鈕 | **8/8** | 1.00 | 1.5 秒 |
| 文字候選＋只描述目標 | 同上；問題只說目標，例如「查看系統寄給我的補償物品」，不說「郵件」 | 文字按鈕 | **8/8** | 0.97 | 0.5 秒 |
| 編號標記＋只描述目標 | 在截圖上每個元素畫黃色編號，選項是編號 | 文字按鈕 | **8/8** | 0.96 | 1.0 秒 |
| 編號標記＋只描述目標 | 同上 | **純圖示** | **4/4** | 0.99 | 0.8 秒 |
| 兩段式格子＋只描述目標 | 不需要候選：先在 12×8 格選一格，再放大附近區域用 6×6 格選一次 | 文字按鈕 | **8/8**（點擊位置落在按鈕內） | 0.48 | 2.4 秒 |
| 兩段式格子＋只描述目標 | 同上 | **純圖示** | **4/4** | 0.41 | 1.9 秒 |

**結論**：

- **可以，而且很準**。在單步選擇上，「為了達成目標該點哪個」和「這是什麼畫面」一樣準；連沒有文字的圖示（信封＝信件、齒輪＝設定、鈴鐺＝通知）也全部選對。
- **編號標記是最好的做法**：準、快（約 1 秒）、信心值高，又不依賴文字。前提是程式要先找出畫面上「可以點的東西」：網頁用 DOM，桌面要用 OCR 加上輪廓或按鈕偵測。
- **兩段式格子不需要偵測器，點擊位置全部正確，但信心值只有 0.4–0.6**。原因是目標通常橫跨好幾格，機率被相鄰格子分掉了。所以它不能套用 0.8 的門檻，要改成「把相鄰格子的機率加總」或另訂較低的門檻；它適合當偵測器找不到候選時的備案。
- **新發現的限制：Decisions API 免費版每分鐘上限 50,000 個輸入 token**。第一次執行時，連續送了大量截圖（格子第二段還是放大 3 倍的圖），撞到這個上限。依代理人模型的用量紀錄，一張截圖大約 1,000–1,800 token，換算每分鐘大約只能處理 25–40 張截圖。程式要對 Decisions 做 token 節流，送出前也要先縮小截圖。

**這次沒驗證到的**：

- 候選框是直接用測試資料的正確答案（等於假設偵測器完美）。真實遊戲要靠 OCR 和偵測器，漏抓或多抓都會影響結果。
- 只測了「一步就能達成」的目標。像「先開任務頁 → 領取 → 回主選單」這種多步流程，還是需要規劃。比較合理的分工是：規劃模型拆出子目標，Decisions API 逐步執行每個子目標。

### 2.5 配額與錯誤（從錯誤訊息取得）

| 模型 | 每分鐘 | 每天 | 來源 |
|---|---|---|---|
| `gemini-4-hydrogen` | 未知 | **20** | 429 訊息 |
| `gemini-3.8-flash` | 未知 | 未知 | 一直 503 |
| `gemini-3.6-flash` | **5** | **20** | 429 訊息 |
| `gemini-3.5-flash-lite` | 未知 | 未知（今天用了約 20 次還沒撞到） | — |
| `gemini-decision-1` | 200（另有**每分鐘 50,000 輸入 token**） | 10,000 | 官方文件；token 上限來自 429 訊息 |

- 429 訊息裡會寫「`Please retry in 59m51s`」，時間點對得上太平洋時間午夜重置。程式可以直接解析這段文字，算出恢復時間。
- 延遲變化很大：同一個模型 3 秒到 35 秒都有；Hydrogen 和 3.8 Flash 各出現過一次 90 秒逾時。

## 3. 對設計的影響

| 發現 | 要改的地方 |
|---|---|
| 原生 `computer_use` 隨機被安全分類器擋下 | 預設 `backend: custom_fc`；`native_cu` 保留為設定選項。被 400 擋下時，同一步改用 `custom_fc` 重送 |
| `custom_fc` 點擊非常準 | 第一版不需要額外的座標校正 |
| 代理人模型每天合計大概只有 60–100 次（視 3.5 Flash-Lite 和 3.8 Flash 的上限而定） | 選單式遊戲：第一次學習時可能就用掉大半天的額度；第二次以後要靠技能重播加 Decisions API。**即時模式（Minecraft）在免費版幾乎不可行**：砍一棵樹就可能需要 30–60 步 |
| 3.6 Flash 每分鐘只有 5 次 | ModelRouter 必須確實執行每分鐘的節流（FR-203），不能等撞到 429 才處理 |
| 503 很常見，連續幾十分鐘都有 | FR-204a 的「重試後暫時停用、換下一個模型」是必要的 |
| 429 訊息裡有恢復時間 | `quota.py` 解析 `retry in XmYs`，比自己推算更準 |
| 單步延遲 3–35 秒 | 前端要顯示「等待模型回應中」，並提供停止按鈕；逾時設為 90 秒 |
| Decisions API 又快又準，配額充足 | 盡量把判斷工作交給它：畫面狀態、是否卡住、是否完成、是否高風險 |

## 4. 模型分工（已決定：依工作分工，2026-11-23）

> 已採用下方建議，寫入 SRS FR-201 與 SDD 4.4。

目前的退階鏈是 Hydrogen → 3.8 Flash → 3.6 Flash → 3.5 Flash-Lite，**每一步都先用 Hydrogen**。但 Hydrogen 一天只有 20 次，又是最慢的（35–45 秒）。照目前的順序，每天前 20 步會又慢又一下就把最強的模型用完。

建議改成**依工作分配模型**：

| 工作 | 建議使用 | 理由 |
|---|---|---|
| 每一步的操作（點擊、按鍵） | 3.5 Flash-Lite → 3.6 Flash → 3.8 Flash | 驗證中最快、最準；配額看起來最多 |
| 規劃子目標、卡住時反思、整理心得 | Hydrogen → 3.8 Flash | 次數少，但需要比較強的推理能力 |
| 畫面判斷、風險判斷、完成檢查 | Decisions API | 每天 10,000 次，每次 0.7 秒 |

## 5. 這次驗證的限制

- **測試畫面都是合成的**，比真實遊戲乾淨很多。真實遊戲有特效、半透明介面、小圖示，準確度一定會下降。P2 開始時要用崩鐵國際服的真實截圖重測。
- 每個模型只測了 4–8 次，樣本很小。
- Hydrogen 和 3.8 Flash 因為配額和 503，幾乎沒測到點擊準度。
- 3.5 Flash-Lite 和 3.8 Flash 的每日上限還不知道。
